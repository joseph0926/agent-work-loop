## 1. 한 장 요약

루프의 중심은 실제 작업이다. 작업 중 생긴 실패는 inbox에, 사람의 화면 판정과 시편 선택은 taste에 쌓인다. mirror는 대화 기록과 여러 저장소의 상태를 읽어 할 일로 보여 준다. 이 기록들이 각 경로를 거쳐 다음 작업에 반영된다 [S5][S6][S7]. harness는 작업에 적용할 전역 규칙과 스킬의 원본을 관리하고 배포한다. taste와 mirror의 본체와 기록은 tools가 소유한다 [S1][S3][S4].

판단과 승인의 역할은 흐름마다 다르다. taste의 최종 판단은 사용자가 한다. mirror에서는 사용자가 메뉴바의 프롬프트를 복사해 에이전트에 요청하고, 에이전트가 내용을 검토하고 처리한다. 실패 inbox의 규칙 승격 검토도 이 경로로 시작한다. 에이전트가 승격할 항목을 보고하면 사용자가 반영을 요청하고, 에이전트가 규칙을 수정한다 [S17]. 도구의 유지와 은퇴는 사용 기록과 수요를 보고 필요할 때 결정한다 [S4][S11][S13][S14].

그림: [루프 한 바퀴](ai-work-loop-2026-10-16.html#loop)

가장 짧게 닫힌 사례: 2026-10-09에 같은 날 만든 도구 `huddle`을 실사용 없이 은퇴시켰고, 그 실패가 같은 날 전역 규칙 한 줄("새 도구나 자동화를 만들 때 비슷한 도구의 은퇴나 낮은 수요 근거가 있으면 먼저 제시하고 확인한다")이 됐다 [S12][S13].

## 3. 루프를 이루는 역할과 흐름

아래는 실제 작업, 작업에 적용할 규칙, 기록과 후속 처리의 역할을 설명한다. 실패 inbox의 승격 검토는 mirror의 요청 경로를 이용하며, taste는 자체 취향 규칙을 다음 화면 작업에 전달한다 [S5][S6][S7][S17].

### 3.1 실제 작업과 판단 주체

- **무엇:** 사람이 요청하고 에이전트가 작업한다. 정정, 되돌림, 범위위반, 같은 원인의 반복 실패는 기록과 검토의 재료가 된다 [S5].
- **판단과 승인:** taste에서는 사용자가 화면을 보고 최종 판단한다. mirror의 후속 작업과 실패의 규칙 승격 검토는 사용자가 에이전트에 맡긴다. 규칙 승격은 에이전트의 제안을 보고 사용자가 반영을 요청하는 순서다 [S17].
- **조사 머신의 실행 설정:** Claude Code는 권한 확인 없이 실행하는 모드다. 대신 `settings.json`의 거부 목록이 `rm -rf`, `git reset --hard`, `git checkout --`, `git clean -f`, `git branch -D`, `git push`와 `.env` 읽기를 막는다 [S9]. Codex는 승인 요청(`on-request`)과 작업 폴더 쓰기(`workspace-write`)다 [S10].
- **약한 고리:** 정정은 표지 없이 사실 진술로 오는 경우가 많아 정규식으로 잡기 어렵다. 2026-10-05 측정에서 사용자 발화 정규식의 정밀도는 0.24였다. 이 값은 위키 요약에서만 확인했다 [S14].

### 3.2 작업 규칙의 원본

- **무엇:** 머신 세 대(personal, work, window)의 전역 규칙과 스킬 원본을 harness 한 곳에서 관리한다. 홈의 파일은 배포본이다 [S3].
- **taste와 mirror의 원천:** taste는 사람의 디자인 판정과 시편 선택을 받고, mirror는 대화 기록과 여러 저장소의 상태를 읽는다. harness는 mirror의 관측 대상 중 하나다 [S6][S7].
- **규모:** personal 규칙은 CLAUDE.md 72줄, AGENTS.md 70줄, environment.md 4줄, 공통 코딩 룰 29줄로 모두 175줄이다. 스킬은 Claude용 11개, Codex용 11개다 [S3].
- **관리 방침:** CLAUDE.md와 AGENTS.md는 벤더 권고가 달라 일부러 다르게 둔다. 한쪽을 고쳤다고 다른 쪽을 따라 고치지 않는다 [S4].
- **약한 고리:** 규칙이 커지고 있다. 검증기 `validate-global-rules.py`는 649줄이다 [S3]. 가운데점을 쓰지 않는다는 규칙을 personal CLAUDE.md가 스스로 3곳에서 어긴다 [S3].

### 3.3 배포

- **무엇:** 배포 표가 대상의 유일한 정의다. `deploy-global-rules.py`가 규칙을, `sync-home.py`(2026-10-15 추가)가 규칙과 스킬을 함께 홈에 맞춘다. 둘 다 기본은 비교만 하고 `--apply`일 때만 쓴다 [S4].
- **조사 당시 상태:** `~/.claude`에는 CLAUDE.md와 `rules/code-quality.md`, `~/.codex`에는 AGENTS.md, code-quality.md, environment.md, mermaid.md가 있다 [S9][S10].
- **적용 절차:** 배포 표에 따라 적용하며, work와 window 머신은 각 머신에서 따로 배포한다 [S4].
- **약한 고리:** 배포 스크립트가 649줄 검증기를 불러 쓰고, `sync-home.py`는 배포 스크립트와 스킬 검증기를 다시 불러 쓴다 [S3].

### 3.5 다음 작업에 반영

- **실패 inbox → mirror → 규칙 반영:** 에이전트가 실패를 기록하고, 같은 owner에 2건이 쌓이면 mirror에 승격 검토가 뜬다 [S5][S7]. 사용자가 메뉴바의 프롬프트를 복사해 Codex나 Claude Code에 검토를 요청한다. 에이전트가 규칙으로 승격할 항목을 보고하면 사용자가 반영을 요청하고, 에이전트가 해당 규칙을 수정한다 [S17]. 전역 규칙과 스킬은 harness로, 저장소 전용 규칙은 해당 저장소로 돌아간다. 처리한 inbox 줄은 지우며 기각한 줄도 지운다. 최초 조사 당시에는 작업 저장소 owner 하나가 2건으로 승격 후보 상태였다 [S5].
- **taste → 다음 화면 작업:** 사용자가 화면과 시편을 보고 최종 판단한다 [S17]. 에이전트와 도구가 이를 취향 규칙과 선호로 정리하고, `tools/taste`가 원장과 규칙을 관리한다. 화면 작업 요청이 들어오면 `UserPromptSubmit` 훅이 관련 규칙과 고른 값을 전달한다 [S6]. 최초 조사 머신에서는 이 훅이 `~/.claude/settings.json`과 `~/.codex/hooks.json`에 모두 걸려 있었다 [S9][S10].
- **mirror → 해당 활동:** 도구가 대화 기록과 저장소 상태에서 신호와 할 일을 만든다. 사용자는 메뉴바의 프롬프트를 복사해 에이전트에 요청하고, 에이전트가 내용을 검토하고 처리한다 [S17]. 학습, 구직, 규칙 정비 등으로 이어지며, 실패 inbox의 승격 검토도 이 요청 경로를 이용한다. 완료 표시와 해소 확인은 나뉘고, 자동 판정이 가능한 신호는 다음 분석에서 사라져야 해소로 친다. 신호에는 harness 원본과 홈 배포본의 차이, inbox 승격 후보, 학습 공백, 4주 반복 요청 같은 것이 있다 [S7].
- **약한 고리:** inbox에서 처리한 21건 가운데 규칙에 넣은 것과 기각한 것은 따로 기록되지 않는다. 그래서 몇 건이 실제 규칙이 됐는지는 셀 수 없다 [S5].

사용 기록과 최근 수요를 보고 규칙, 스킬, 도구를 유지하거나 고치거나 버린다. 운영 중 필요할 때 내리는 판단이다 [S4][S11][S13][S14].

## 5. 결정 사례 다섯 건

다시 쓸 때 가장 중요한 부분이다. 각 사례는 시도, 기록으로 본 결과, 바꾼 것, 그 뒤 순서다.

**2026-10-01 실패 원장을 inbox로.** 시도: 2026-08-09부터 모든 실패를 append-only 원장에 남기고 처리 기록을 따로 남겼다. 결과: 638건 가운데 544건(85.3%)이 검증실패였고, 처리 기록은 275건에서 2026-09-05 이후 멈췄다. 바꾼 것: `fix_line`을 쓸 수 있는 실패만 남기고 처리하면 지우는 inbox. 이후: 16일 동안 최소 32건 기록, 21건 처리 [S5][S4].

**2026-10-05 누적 수치보다 최근 2주.** 시도: 3개월 기록에서 가장 큰 마찰(두 에이전트 사이 수동 중계, 약 94세션)을 위임 도구로 풀었다. 결과: 최근에는 그 일이 드물어 두 도구를 제거했고, 최근 2주 기록으로 9개 방향을 시험해 모두 만들지 않았다. 바꾼 것: tools 저장소 규칙 "새 도구를 만들기 전에 최근 2주 기록으로 지금도 필요한지 확인"(2026-10-10 커밋) [S14][S15].
